# 银行数据分析工作流生成智能体 · 详细设计方案

> 版本：v0.1（草案）｜ 状态：待评审 ｜ 执行层路线：**平台工作流（Dify / DB-GPT AWEL）**
> 调研基础：MetaGPT Data Interpreter、Data-Copilot、TaskWeaver、DB-GPT、ml-approach-suggestion-agent（详见调研汇报）

---

## 1. 项目概述

### 1.1 目标

构建一个智能体：用户用一句自然语言说出分析需求，智能体自动完成：

1. **判断问题类型**（分类 / 聚类 / 归因 / 预测 / 取数问答）；
2. **列出工作流流程**（人类可读的步骤清单 + DAG 图）；
3. **自动生成可导入平台的工作流**（Dify DSL 或 DB-GPT AWEL 代码）；
4. 辅助产出**分析结果**：名单、图表、结论文本。

### 1.2 核心用户故事（贯穿全文档的示例）

> 用户输入："根据现有的使用公积金服务用户特征，找出潜在的开通服务名单。"

期望行为链路：

1. 路由 Agent 判定：**分类分析（响应率预测 / Look-alike 打分）**
   - 依据：存在天然标签（现有公积金用户 = 1，非用户 = 0）+ 产出物是"名单"（打分排序）。
2. 规划 Agent 输出流程清单（示例）：
   - ① 取数：客户主表 + 公积金开通标记 + 行为/资产特征
   - ② 特征工程：缺失值处理、类别编码、WOE/分箱、特征筛选
   - ③ 建模：LightGBM/XGBoost/LR 候选训练 + 5 折交叉验证
   - ④ 评估：AUC/KS/Lift，输出特征重要性
   - ⑤ 打分：对未开通客户打响应概率分，Top-N 排序
   - ⑥ 名单输出：Excel/推送，附客户号、分数、可解释因子
   - ⑦ 报告：方法说明、效果指标、营销建议
3. 编译器把上述 DAG 编译为 Dify YAML DSL（或 AWEL Python），用户一键导入平台运行。

### 1.3 设计原则

| 原则 | 说明 |
|---|---|
| **IR 解耦** | 自定义中间表示（IR DAG JSON），路由/规划不绑定平台；换平台只换编译器 |
| **模板优先，生成兜底** | 先匹配业务模板再让 LLM 微调参数，而非从零生成，稳定性大幅提高（借鉴 Data-Copilot 的"先设计接口库、再调度"思想） |
| **路由可解释** | 每次判定必须输出"依据 + 置信度"，低置信度时反问澄清，不硬猜 |
| **重计算外置** | LLM 只负责规划与编排，建模计算走代码节点/算法服务，规避沙箱限制 |

## 2. 总体架构

```
┌─────────────────────────────────────────────────────────┐
│ ① 交互层（Web 对话框 / CLI）                              │
│    用户需求 → 展示判定结论 → 展示流程清单 → 导出工作流文件   │
├─────────────────────────────────────────────────────────┤
│ ② 范式路由 Agent（Intent Router）                         │
│    输入需求 + 数据画像 → 输出 ParadigmDecision JSON        │
│    （低置信度 → 生成澄清问题，回到交互层）                  │
├─────────────────────────────────────────────────────────┤
│ ③ 工作流规划 Agent（Planner）                             │
│    模板匹配 → 参数填充 → LLM 修正 → IR DAG JSON            │
├─────────────────────────────────────────────────────────┤
│ ④ 编译层（Compiler）                                      │
│    IR → Dify YAML DSL（0.7.0）                            │
│    IR → DB-GPT AWEL Python                                │
├─────────────────────────────────────────────────────────┤
│ ⑤ 执行与输出层                                            │
│    平台内运行（Dify/DB-GPT）+ 算法服务（Python 沙箱/服务）  │
│    产出：名单 Excel / 图表 / Markdown 分析报告             │
└─────────────────────────────────────────────────────────┘
   横切资产：模板库（T1~T4）｜银行字段元数据｜LLM 网关
```

### 技术选型

| 组件 | 选型 | 理由 |
|---|---|---|
| 语言 | Python 3.11+ | 生态一致 |
| LLM | 行内可用模型（DeepSeek/通义等，OpenAI 兼容接口） | 仅做路由/规划/修正，不跑模型训练 |
| Schema 校验 | pydantic v2 | IR 与路由输出强校验 |
| 编译目标 A | **Dify DSL（version 0.7.0，mode: workflow）** | YAML 可读、导入即用、社区模板多 |
| 编译目标 B | DB-GPT AWEL（`dbgpt.core.awel.DAG`） | 私有化数仓场景常用，Operator 生态全 |
| 建模算法 | scikit-learn / LightGBM / SHAP / DoWhy | 三类分析的标准件 |

## 3. 模块详细设计

### 3.1 范式路由 Agent（Intent Router）

#### 输入

```json
{
  "user_request": "根据现有的使用公积金服务用户特征，找出潜在的开通服务名单",
  "data_profile": {                      // 可选；无表结构信息时靠澄清问题补齐
    "tables": [{"name": "cust_info", "columns": ["cust_id", "is_gjj_user", "age", "assets", "txn_cnt"]}]
  }
}
```

#### 输出（ParadigmDecision，pydantic 强校验）

```json
{
  "paradigm": "classification",
  "confidence": 0.9,
  "rationale": "需求中存在天然标签『现有公积金用户』，且产出物为『名单』，属于二分类响应预测（Look-alike）场景",
  "candidates": [{"paradigm": "clustering", "reason": "若用户实际想要分层营销策略", "needs_clarification": true}],
  "clarifying_questions": [],            // confidence < 0.7 时非空
  "matched_template": "T1_response_prediction"
}
```

#### 判定规则表（Prompt 内置的决策依据，LLM + 规则双通道）

| 信号组合 | 判定 | 模板 |
|---|---|---|
| 有历史标签（已开通/已流失/已响应）+ 要"名单/排名" | **分类**（响应预测/打分） | T1 |
| 无标签 + "分群/分层/画像差异" | **聚类** | T2 |
| "为什么/哪些因素导致/原因是什么" | **归因** | T3 |
| "预测未来数值/趋势/多少" | 预测（回归/时序） | T4 扩展 |
| 只查数、算指标、做报表 | Text2SQL 取数问答 | T5 兜底 |
| 要"名单"但**无标签** | 聚类分群 + 群内相似度扩展；**必须澄清** | T1/T2 |

#### 双通道策略

- **规则通道**：正则/关键词 + 标签字段探测，先跑一遍；
- **LLM 通道**：few-shot 8 个银行场景示例，输出 JSON；
- 两通道一致 → 直接通过；不一致或 confidence < 0.7 → 触发澄清问题（最多 2 问）。

#### Router Prompt 骨架

```
你是银行数据分析范式路由器。根据用户需求和数据画像，判定分析范式。
可选范式：classification / clustering / attribution / forecasting / text2sql
判定依据（内置规则表）：{RULES}
参考样例：
  1. "根据已流失客户特征找出可能流失客户" → classification（有标签+名单）
  2. "把客户按消费行为分成几类做差异化营销" → clustering（无标签+分群）
  3. "分析是什么因素导致理财客户流失" → attribution（问原因）
输出 JSON：{paradigm, confidence, rationale, candidates, clarifying_questions}
```

### 3.2 工作流规划 Agent（Planner）

**两段式规划（关键设计，不纯靠生成）：**

1. **模板填充**：按 `matched_template` 取对应 IR 骨架，填入需求中的表名/字段/参数；
2. **LLM 修正**：把填充后的 IR 交给 LLM，仅允许做受限修改（增删可选节点、改参数、改节点描述），禁止改 schema；pydantic 校验不通过则自动重试（最多 3 次）。

#### IR DAG JSON Schema（核心结构）

```json
{
  "workflow_id": "wf_gjj_potential_list_001",
  "name": "公积金潜在开通客户名单",
  "paradigm": "classification",
  "source_request": "根据现有的使用公积金服务用户特征，找出潜在的开通服务名单",
  "inputs": [
    {"name": "cust_info", "type": "table", "desc": "客户主表，含 is_gjj_user 标记"}
  ],
  "nodes": [
    {"id": "n1", "type": "data_query",          "name": "取客户样本",   "params": {"sql": "...", "label_col": "is_gjj_user"}},
    {"id": "n2", "type": "feature_engineering", "name": "特征工程",     "params": {"missing": "median", "encode": "woe", "select": "iv_top50"}},
    {"id": "n3", "type": "model_train",         "name": "训练响应模型", "params": {"algos": ["lightgbm", "xgboost", "lr"], "cv": 5}},
    {"id": "n4", "type": "model_eval",          "name": "模型评估",     "params": {"metrics": ["auc", "ks", "lift10"]}},
    {"id": "n5", "type": "score_predict",       "name": "全量打分",     "params": {"scope": "未开通客户"}},
    {"id": "n6", "type": "list_output",         "name": "输出名单",     "params": {"top_n": 50000, "format": "excel", "explain": true}},
    {"id": "n7", "type": "report_generate",     "name": "生成分析报告", "params": {"lang": "zh"}}
  ],
  "edges": [{"from": "n1", "to": "n2"}, {"from": "n2", "to": "n3"}, {"from": "n3", "to": "n4"},
            {"from": "n3", "to": "n5"}, {"from": "n5", "to": "n6"}, {"from": "n4", "to": "n7"}, {"from": "n6", "to": "n7"}],
  "outputs": [{"name": "potential_list", "type": "file"}, {"name": "report", "type": "markdown"}]
}
```

同时 Planner 输出人类可读的"流程清单"（Markdown 有序步骤 + Mermaid 图），在交互层先展示给用户确认后再编译。

### 3.3 模板库（核心资产，银行业沉淀）

| ID | 名称 | 范式 | 节点序列（IR 骨架） | 关键算法 |
|---|---|---|---|---|
| T1 | 响应率预测/潜在客户挖掘 | 分类 | 取数→特征→训练→评估→打分→名单→报告 | LightGBM/XGBoost/LR，KS/AUC/Lift，SHAP 可解释因子 |
| T2 | 客户细分 | 聚类 | 取数→特征标准化→K 值选择→聚类→群画像→策略建议→报告 | KMeans/GMM，轮廓系数，群画像透视 |
| T3 | 归因分析 | 归因 | 取数→分组对比→显著性检验→特征重要度→因果检验→报告 | SHAP、PSM 配对、DoWhy 因果图（M4 增强） |
| T5 | 取数问答 | text2sql | NL→SQL→执行→图表→结论 | DB-GPT ChatBI 能力 / Dify LLM+code 节点 |

每个模板包含：IR 骨架 JSON、变量槽位表（哪些必须澄清、哪些有默认值）、few-shot 示例 2 条、预期产出物清单。

### 3.4 编译器（IR → 目标平台）

#### 目标 A：Dify DSL（主推）

映射表（节点级）：

| IR 节点类型 | Dify 节点（`data.type`） | 说明 |
|---|---|---|
| data_query | `http-request`（调数仓/取数 API）或 `code` | 生成 SQL 由上游 LLM 节点产出 |
| feature_engineering / model_train / model_eval / score_predict | `http-request` → 行内 Python 算法服务 | **重计算外置**，规避 Dify code 沙箱依赖限制 |
| if-else 分流（低/高分策略） | `if-else` | sourceHandle = true/false |
| list_output | `code`（整理）+ `template-transform` | 文件经算法服务回传 URL |
| report_generate | `llm` + `template-transform` + `end` | 汇总上游变量 `{{#node_id.field#}}` |

生成骨架示例（节选，完整以 Dify 1.16 `version: "0.7.0"` 规范）：

```yaml
app:
  name: "公积金潜在开通客户名单"
  mode: workflow          # 一次性批量任务用 workflow，不用 advanced-chat
  icon: "🏦"
kind: app
version: "0.7.0"
dependencies: []
workflow:
  graph:
    nodes:
      - {id: "start", type: custom, data: {type: start, title: 开始, variables: [...]}}
      - {id: "n1",    type: custom, data: {type: http-request, title: 取客户样本, ...}}
      - {id: "n3",    type: custom, data: {type: http-request, title: 训练响应模型, ...}}
      - {id: "end",   type: custom, data: {type: end, title: 结束, outputs: [...]}}
    edges:
      - {source: "start", target: "n1", data: {sourceType: start, targetType: http-request}, type: custom}
    viewport: {x: 0, y: 0, zoom: 0.8}
```

编译器需遵守的导入敏感细节：ID/版本号加引号、`sourceType/targetType` 与端点节点 `data.type` 同步、workflow 模式必须有 `end` 节点、节点间变量用 `value_selector` 二元选择器。

#### 目标 B：DB-GPT AWEL（备选，私有化数仓场景）

每个 IR 节点 → 一个自定义 Operator（继承 `MapOperator`），顺序依赖用 `>>` 串联：

```python
from dbgpt.core.awel import DAG
from bank_ops import (DataQueryOperator, FeatureOperator, TrainOperator,
                      EvalOperator, ScoreOperator, ListOutputOperator)

with DAG("wf_gjj_potential_list_001") as dag:
    n1 = DataQueryOperator(sql=..., label_col="is_gjj_user")
    n2 = FeatureOperator(missing="median", encode="woe")
    n3 = TrainOperator(algos=["lightgbm", "xgboost", "lr"], cv=5)
    n4 = EvalOperator(metrics=["auc", "ks", "lift10"])
    n5 = ScoreOperator(scope="未开通客户")
    n6 = ListOutputOperator(top_n=50000, fmt="excel")
    n1 >> n2 >> n3 >> (n4, n5)
    n5 >> n6
```

#### 两目标对比与建议

| 维度 | Dify | DB-GPT AWEL |
|---|---|---|
| 导入体验 | 界面一键导入 YAML | 需注册 Operator 后运行 Python |
| 可视化编排 | ✅ 成熟画布 | 弱（偏代码） |
| 数仓/私有化亲和 | 中（走 HTTP） | 强（内置数据源连接） |
| 建议 | **M2 先做**，覆盖 80% 场景 | M4 可选增强 |

### 3.5 执行、回填与报告

- 工作流在平台（Dify/DB-GPT）内运行；建模步骤调**行内算法服务**（FastAPI + 沙箱执行器，队列化）。
- 运行完成后：名单落 Excel/推送 CRM；指标与图表回填交互层；报告由 LLM 按"方法说明→数据口径→模型效果→名单使用建议"固定骨架生成。

## 4. 关键设计决策（ADR）

| # | 决策 | 理由 |
|---|---|---|
| D1 | 引入 IR 中间表示而非直接生成平台 DSL | 平台演进快（Dify 0.7.0 变更频繁），IR 稳定且可测试 |
| D2 | 模板填充 + 受限 LLM 修正，而非自由生成 | 银行场景重稳定性；纯生成的 DAG 不可控 |
| D3 | 重计算外置到算法服务 | Dify code 沙箱装 sklearn/LightGBM 受限，AWEL 也需自写 Operator |
| D4 | 路由层做显式"范式判定"并输出依据 | 现有开源（Data Interpreter 等）都是隐式拆解，这是本项目的差异化价值点 |
| D5 | 归因分析 M4 再做，先 SHAP 后 DoWhy | 归因开源空白最大，风险最高，先统计后因果渐进 |

## 7. 风险与对策

| 风险 | 对策 |
|---|---|
| LLM 误判范式 | 规则+LLM 双通道一致才放行；confidence<0.7 必澄清；每次输出 rationale 供人工复核 |
| Dify DSL 版本碎片 | 编译器按目标版本参数化；导入失败时输出修复建议 |
| 银行数据安全 | 全流程仅传表结构元数据给 LLM，不传行级数据；算法服务可内网部署 |
| 名单合规 | 输出节点强制带"营销合规提示"模板字段 |

## 8. 需求方确认结论（已答复）

| 问题 | 结论 | 对设计的影响 |
|---|---|---|
| 数据源 | 华为 TD 数仓，但取数不需要 SQL，**由人工上传** | v1 数据接入改为「Dify start 节点文件上传 + 算法服务解析」，TD/GaussDB 连接器列为 M5+ 可选扩展 |
| 平台 | **Dify 已部署**，模型配置文件直接上传可用 | 只实现 Dify 编译器（主路线）；AWEL 编译器降为 M5 可选 |
| LLM | **DeepSeek 4 Flash**（行内命名） | Router/Planner/报告全部走 OpenAI 兼容接口 + JSON mode，model.provider 做成编译器配置项对齐行内 Dify 已配置供应商 |
| 名单出口 | **暂时 Excel 落地** | list_output 直接生成 Excel 下载链接，不做 CRM 推送 |
| 归因深度 | 未答复，按默认处理 | M4 先 SHAP 统计归因，DoWhy 因果推断列为可选项 |
