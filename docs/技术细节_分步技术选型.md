## 0. 确认结论对架构的落地影响

| 确认项 | 架构调整 | 技术动作 |
|---|---|---|
| 取数不需要 SQL，人工上传 | 删掉 `data_query→SQL` 环节，改为「Dify start 节点文件输入 + 算法服务解析」 | 算法服务新增 `/ingest` 接口（pandas 解析 Excel/CSV） |
| Dify 已部署、模型配置文件直接上传可用 | 智能体只负责「产出 DSL 文件」，不负责装模型 | 编译器把 `model.provider` / `model` 做成配置项，对齐行内已配置的 DeepSeek 供应商 |
| DeepSeek 4 Flash | 三个 LLM 使用点统一走 OpenAI 兼容协议 | `openai` Python SDK + `base_url` 指向行内端点，JSON mode 输出 |
| 名单暂时落地 | 名单输出即终点 | 算法服务生成 Excel 并提供下载 URL，无 CRM 推送模块 |

## 1. 端到端时序（谁在哪一步干什么）

```
分析师        智能体服务            DeepSeek          Dify(已部署)        算法服务(自研)
  │ ①需求文本 ──▶│                     │                 │                   │
  │             │ ②范式路由 ─────────▶│                 │                   │
  │             │◀─ ParadigmDecision ─│                 │                   │
  │             │ ③模板规划+LLM修正 ──▶│                 │                   │
  │ ◀─ ④流程清单+IR确认 ─│             │                 │                   │
  │             │ ⑤编译 → .yml DSL    │                 │                   │
  │ ⑥导入DSL、上传Excel、点运行 ─────────────────────────▶ │                   │
  │             │                     │                 │ ⑦/ingest ───────▶ │ pandas 解析
  │             │                     │                 │ ⑧/analysis/run ▶  │ 特征/训练/评估/SHAP/名单
  │             │                     │   ⑨LLM 节点生成分析报告              │
  │ ◀─ ⑩名单Excel下载URL + Markdown报告 ────────────── end │                   │
```

①~⑤ 是**智能体侧**（规划期），⑥~⑩ 是 **Dify 运行期**。两期只通过 DSL 文件衔接。

## 2. 智能体侧 · 分模块技术栈（我们自己写的代码）

| 模块 | 职责 | 技术选型 | 说明 |
|---|---|---|---|
| 交互层（M1 CLI） | 收需求、展示判定与流程、导出 DSL | `typer` + `rich`（表格/树形展示流程清单） | M3 可升级 FastAPI + 简易前端 |
| 范式路由 Router | 判定分类/聚类/归因/预测/取数 | `openai` SDK（`base_url`=DeepSeek 端点）+ **JSON mode**（`response_format={"type":"json_object"}`，temperature 0.1） | LLM 通道 |
| ├ 规则通道 | 标签列探测、关键词命中 | `re` + `pandas`（读上传文件的表结构做 0/1 标签探测） | 与 LLM 双通道比对，不一致必澄清 |
| ├ 输出校验 | ParadigmDecision 强约束 | `pydantic` v2 | 校验失败自动重试 ≤3 次 |
| ├ 重试与日志 | 稳定性 | `tenacity` + `loguru` | LLM 超时/限流退避重试 |
| 工作流规划 Planner | 模板填充 + 受限修正 | `jinja2`（模板渲染）+ `pydantic`（IR 模型）+ DeepSeek JSON mode（temperature 0.2，仅允许改参数/增删可选节点） | 输出 IR DAG JSON |
| 模板库 | T1/T2/T3/T5 骨架 | JSON 文件 + `jsonschema` 校验槽位 | 银行业沉淀资产 |
| Dify 编译器 | IR → DSL 0.7.0 YAML | `PyYAML`（safe_dump，`allow_unicode`）+ `jinja2`（节点模板）+ 自研分层布局 | 主路线 |
| ├ 布局器 | 节点 x/y 坐标 | 自研：拓扑分层（`graphlib.TopologicalSorter`）→ 按层排 x、层内排 y | 保证画布可读 |
| ├ ID 生成器 | 节点/边 ID | 毫秒时间戳字符串（对齐 Dify 导出习惯：`"1770000000000"`） | ID 加引号 |
| DSL 校验器 | 导入前自检 | `yaml.safe_load` + 自研规则：version 加引号、`end` 节点存在、`sourceType/targetType` 与端点 `data.type` 同步、`value_selector` 二元格式 | 防导入失败 |
| 测试 | 黄金用例回归 | `pytest`（公积金/流失/细分/归因 4 条端到端 + DSL 断言） | |

## 3. 生成出的 Dify 工作流 · 逐节点技术（运行期，T1 公积金案例）

生成的 DSL（`mode: workflow`，version "0.7.0"）节点序列：

| # | Dify 节点 `data.type` | 干什么 | 节点内技术/配置 |
|---|---|---|---|
| 1 | `start` | 分析师上传数据 + 填参数 | 变量：`file`（files 类型，`local_file` 上传）+ `top_n`（number）+ `label_col`（text，默认自动探测） |
| 2 | `http-request` | 上传文件给算法服务 | `POST {ALGO}/api/v1/ingest`，multipart；返回 `dataset_id` + schema 摘要 |
| 3 | `code` | 解析响应 | **仅标准库**（`json`），取字段拼下游入参——Dify code 沙箱默认没有 pandas，这是「重计算外置」的直接原因 |
| 4 | `if-else` | 校验分流 | sourceHandle=`true`/`false`（DSL 0.7.0 规范） |
| 5 | `http-request`（true 分支） | 触发分析 | `POST {ALGO}/api/v1/analysis/run`（body: dataset_id + 模板参数）；v1 **同步等待**，节点超时配长（≥10min） |
| 6 | `code` | 解析指标/文件 URL | 标准库 json |
| 7 | `llm` | 生成分析报告 | model = 行内 DeepSeek 4 Flash（provider 名对齐行内配置）；输入 = 指标 JSON（**不含行级数据**），输出 Markdown |
| 8 | `end` | 输出 | `list_url`（Excel 下载链接）+ `report`（Markdown 文本） |

> v2 优化：数据量大时改为 `POST /analysis/submit`（异步返回 task_id）+ Dify `loop` 节点轮询 `GET /analysis/status/{task_id}`（DSL 0.7.0 已支持 loop/loop-start/loop-end）。v1 先同步，实现简单。

## 4. 算法服务 · 逐分析步骤技术（核心计算层）

服务框架：`FastAPI` + `uvicorn`，文件暂存本地磁盘 `/data/{dataset_id}`，`loguru` 记录全过程。

### 4.1 通用入口 `/ingest`

| 步骤 | 技术 |
|---|---|
| 文件接收 | FastAPI `UploadFile` + `python-multipart` |
| 解析 | `pandas.read_excel`（`openpyxl` 引擎）/ `pandas.read_csv` |
| 数据画像 | dtype 推断、缺失率、唯一值数；**标签列探测**：找 0/1 二值列 + 命名含 `开通/响应/流失` 的列 |
| 返回 | `dataset_id` + schema JSON（只给 LLM 看这个，不给行级数据） |

### 4.2 T1 响应率预测（公积金潜在名单 → 分类）

| 步骤 | 技术 | 库 |
|---|---|---|
| 清洗 | 缺失填充（数值中位数/类别众数） | `sklearn.impute.SimpleImputer` |
| 分箱 / WOE / IV | 银行标准卡评分流程 | `toad`（`toad.transform.WOETransformer`、`toad.selection.select`） |
| 特征筛选 | IV > 0.02 → 相关性去重 → 模型重要度 Top-K | `toad` + `numpy` 上三角相关 + LightGBM importance |
| 类别不平衡 | 类权重为主，SMOTE 备选开关 | `class_weight='balanced'` / `imblearn` |
| 训练 | 三算法候选 + 5 折分层交叉验证 + 小网格随机搜索 | `LightGBM`（主）/ `XGBoost` / `LogisticRegression`，`sklearn.model_selection.StratifiedKFold` + `RandomizedSearchCV` |
| 评估 | AUC、KS、Top10% Lift、ROC/KS 图 | `sklearn.metrics` + `toad` KS + `matplotlib`（PNG 存盘） |
| 可解释 | 全局重要度 + 单客户 Top-N 原因因子 | `shap.TreeExplainer` |
| 打分出名单 | 全量 `predict_proba` → Top-N 排序 → 分层（高/中/低） | `pandas` |
| 名单落地 | Excel（客户号、分数、分层、Top3 原因因子、合规提示列） | `pandas.to_excel`（`xlsxwriter`/`openpyxl`） |
| （可选）分数卡刻度 | 300~900 标准评分刻度 | `scorecardpy`（备选，与 toad 二选一） |

### 4.3 T2 客户细分（聚类）

| 步骤 | 技术 | 库 |
|---|---|---|
| 标准化 | 数值标准化 + 类别 one-hot | `sklearn.preprocessing.StandardScaler` / `OneHotEncoder` |
| K 值选择 | 轮廓系数 + 肘部法自动找拐点 | `sklearn.metrics.silhouette_score` + `kneed` |
| 聚类 | KMeans（主）、GMM（备选） | `sklearn.cluster.KMeans` / `mixture.GaussianMixture` |
| 降维可视化 | 2D 散点图 | `PCA`（默认）/ `umap-learn`（可选） |
| 群画像 | 各群特征均值 vs 总体偏差 Top-N | `pandas.groupby` |
| 群命名与策略 | 按画像自动命名 + 营销建议 | DeepSeek（LLM，temperature 0.4） |

### 4.4 T3 归因分析（M4，先统计后因果）

| 步骤 | 技术 | 库 |
|---|---|---|
| 显著性检验 | 卡方 / t 检验 / Cramér's V | `scipy.stats`（`chi2_contingency`、`ttest_ind`）；`dython`（可选） |
| 特征重要度归因 | 代理模型 + SHAP | `LightGBM` + `shap` |
| 倾向得分匹配（可选） | PSM 配对对比 | `psmpy` / `sklearn.neighbors` |
| 因果推断（M4+ 可选） | 因果图 + 反事实 | `dowhy`（`econml` uplift 备选） |

## 5. LLM（DeepSeek 4 Flash）使用点汇总

| 用途 | 调用方 | temperature | 输出约束 | 备注 |
|---|---|---|---|---|
| 范式路由 | 智能体 Router | 0.1 | JSON mode + pydantic 校验 | few-shot 8 条银行场景 |
| 工作流修正 | 智能体 Planner | 0.2 | 受限 JSON（仅参数/可选节点） | 模板已填好，只做微调 |
| 分析报告生成 | Dify `llm` 节点 | 0.4 | Markdown（固定骨架：方法→口径→效果→建议） | 输入只有指标 JSON |
| 聚类群命名 | 算法服务内调用 | 0.4 | JSON | v1 可先规则命名，LLM 增强 |

接入方式统一：`openai` SDK，`base_url`/`api_key`/`model` 三项走环境变量；Dify 侧模型供应商按行内「模型配置文件」为准，编译器生成 DSL 时以配置项 `dify.provider_name`、`dify.model_name` 对齐。

## 6. 关键工程决策与风险

| 决策/风险 | 处理 |
|---|---|
| Dify code 沙箱没有 pandas/sklearn | 所有重计算在算法服务，code 节点只做 JSON 解析（零第三方依赖） |
| 同步等待 vs 异步轮询 | v1 同步 + http-request 长超时；>50 万行数据或超 15 分钟任务，切 v2 的 submit+loop 轮询方案 |
| LLM 输出不稳定 | JSON mode + pydantic 校验 + tenacity 重试（≤3）+ 规则通道兜底 |
| 数据安全 | LLM 只见 schema 与聚合指标；算法服务内网部署；上传文件大小/类型白名单校验 |
| DSL 导入失败 | 编译器内置校验器自检（version 引号、end 节点、edge type 同步、selector 格式）后再落盘 |
