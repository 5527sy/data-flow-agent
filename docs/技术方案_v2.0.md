## 1. 项目定位

**DataFlow Agent：卡片式人机共驾的数据分析 Agent。**

- 用户一句自然语言说需求 → 系统判定分析范式 → 以**向导式卡片流程**逐步执行：
  样本设计 → 取数 → 数据体检 → 清洗特征 → 训练评估 → 名单输出
- 设计哲学：**机器负责算和画，人负责拍板和签字**。每张卡片是一次"系统提案 → 人工审批"。
- 业务首选场景：银行（公积金潜在客户名单为黄金案例），可泛化到任意"响应预测/客户细分/归因"分析。

## 2. 需求确认结论（已锁定）

| 项 | 结论 | 影响 |
|---|---|---|
| 数据源 | 华为 TD 数仓，**取数不直连，由人工执行 SQL** | Agent 生成 SQL + 样本设计方案，人工取数上传（安全合规的现实解） |
| 平台 | Dify 已部署（DeepSeek 已配置） | **降级为可选集成项**（报告生成/工作流导出），不再是主路线 |
| LLM | DeepSeek 4 Flash（OpenAI 兼容接口） | 路由/结论生成用，JSON mode + pydantic 校验 |
| 名单出口 | Excel 落地 | 无 CRM 推送模块 |
| 交互形态 | **卡片式一步步向导**，用户点下一步，卡片滑走 | 见 §6 交互设计 |

## 3. 端到端流程（v2 主线，七张卡片）

```
用户需求（自然语言）
   ↓
┌ ① 需求路由卡 ──────────────────────────────── 系统
│    双通道判定范式：分类 / 聚类 / 归因 / 取数；一致才放行，低置信度必澄清
   ↓
┌ ② 样本设计 + 提数卡 ───────────────────────── 系统+人
│    2a 产出《样本设计方案》：观察期/表现期/正负标签/排除规则/样本量预估
│        → 人工确认后才许出 SQL（防标签泄漏）
│    2b 生成提数 SQL → 【人工执行取数】（数仓权限/安全合规）
   ↓
┌ ③ 取数上传卡 ──────────────────────────────── 人
│    上传数据文件 + 列映射确认
   ↓
┌ ④ 数据体检卡 ──────────────────────────────── 系统+人
│    行数 / 正负样本比 / 缺失率 / 单一值列 / PSI
│    阈值人工可调（默认值预填）；不合格打回②重提数
   ↓
┌ ⑤ 清洗 + 特征工程卡 ───────────────────────── 系统+人
│    日期标准化 / 字典映射 / 缺失填充 / WOE 分箱 / IV 筛选
│    人工可调：分箱方式、IV 阈值、相关性去重阈值
│    ⚠ 清洗规则固化为 pipeline（打分期原样重放）
   ↓
┌ ⑥ 训练评估卡 ──────────────────────────────── 系统+人
│    LightGBM / LogisticRegression / XGBoost + 5 折 CV 调参
│    + OOT 时间外验证 + SHAP 可解释；人工看曲线拍板
   ↓
┌ ⑦ 名单输出卡 ──────────────────────────────── 系统+人
│    剔除存量正样本客户 → 打分排序 → 分层 → 名单 Excel
│    + 《分析方法说明》报告（审计合规刚需）
```

## 4. 风控建模六大专业设计（业务护城河）

| # | 设计 | 说明 |
|---|---|---|
| 1 | **防标签泄漏** | 特征只取观察期内数据；先确认《样本设计方案》再出 SQL；排除规则（存量客户/新户无表现） |
| 2 | **数据体检前置** | 上传先体检（正负比/缺失率/PSI），不合格打回重提数，不让垃圾进建模 |
| 3 | **清洗规则固化重放** | 训练期清洗/分箱/编码规则存为 pipeline 对象，打分期原样重放——口径一致是模型验证岗第一检查项 |
| 4 | **CV 调参 + OOT 验证两段式** | 5 折交叉验证只做调参选型；最终效果用时间上更晚的 OOT 样本评估（客户群体漂移） |
| 5 | **特征按算法差异化** | LR 吃 WOE 特征（评分卡可解释性）；LightGBM/XGBoost 吃原始分箱特征 |
| 6 | **名单合规三件套** | 剔除存量正样本客户；分数+分层+Top3 SHAP 原因因子；合规提示与方法报告 |

## 5. Agent 组件设计

### 5.1 Agent① 范式路由器（分诊台）

- **职责**：听需求 → 判断"这是哪类问题" → 决定走哪条流水线
- **双通道**：规则通道（关键词表，稳定可解释）+ LLM 通道（few-shot 分类，语义灵活）
- **放行规则**：两通道一致且置信度 ≥0.7 → 通过；不一致或低置信 → 生成澄清问题（最多 2 轮）
- **输出契约**：`{paradigm, confidence, rationale, clarifying_questions, matched_template}`（pydantic 校验）

### 5.2 Agent② 样本设计 + 提数助手

- 输入：范式判定 + 数据字典（表/字段/备注/枚举值/表关系）
- 输出：《样本设计方案》（人工确认）→ 提数 SQL（语法自检后交付人工执行）
- 设计要点：SQL 生成依赖**数据语义层**，不只是字段备注；SQL 生成后过静态校验

### 5.3 Agent③~⑦

见 §3 流程图与 §6 卡片明细；共同契约：每步 `run(params) → artifact(产物+图+人话结论) → confirm/reject`。

## 6. 交互设计：卡片式人机共驾

### 6.1 卡片统一五段结构

```
① 任务说明（为什么做） → ② 参数区（默认值预填，人可改）
→ ③ 执行区（运行+进度） → ④ 结果预览（图+指标+一行"人话结论"）
→ ⑤ 决策区（[通过→下一步] [调参重跑] [打回上一步]）
```

### 6.2 七卡片参数与预览明细

| 卡片 | 人工可调参数（默认值预填） | 结果预览 |
|---|---|---|
| ①需求路由 | 确认范式/目标列 | 双通道判定对照卡 |
| ②样本设计 | 时间窗口、标签定义、排除规则、样本量 | 样本时间轴 + 预估正负比 |
| ③取数上传 | 文件上传、列映射 | 前 20 行 + 列清单 |
| ④数据体检 | 最小行数(1万)、正负比告警区间、缺失率剔除线(80%)、单一值阈值 | 缺失率条形图、正负比饼图 |
| ⑤清洗特征 | 分箱方式(卡方)、IV 阈值(0.02)、相关性去重(0.7)、填充策略 | IV 条形图（点开看 WOE 曲线）、前后对比图 |
| ⑥训练评估 | 模型勾选、CV 折数(5)、不平衡策略、OOT 切分点、主指标 | ROC/KS 曲线、重要度 Top20、三模型对比 |
| ⑦名单输出 | Top-N 或分数阈值、分层切点、剔除存量(默认是) | 名单前 100 行、分数分布、预计响应人数 |

### 6.3 六条全局机制

1. **涟漪过期**：上游参数变更 → 下游结果自动标记 ⚠️ 需重跑（依赖链脏标记）
2. **快照回溯**：`outputs/run_{id}/step_{n}_v{版本}/`，可跳回任意步骤重跑、隔天续做
3. **审计日志**：谁/何时/什么参数/通过还是打回/LLM 建议内容——合规刚需
4. **人话结论**：预览区顶部 LLM 生成一行结论（只喂汇总指标，不喂行级数据）
5. **打回路径**：体检不合格→打回②；训练不满意→卡内调参或回退⑤；打回原因入日志
6. **产物引用传递**：卡片间传 dataset_id/pipeline 对象路径，不传数据本体

## 7. 技术选型（v2 定稿）

| 层 | 选型 | 关键理由 |
|---|---|---|
| LLM 接入 | **openai SDK + Instructor + pydantic**（不用 LangChain） | 固定管线不需框架抽象；结构化输出是命脉；依赖树小、内网好审批 |
| LLM | DeepSeek 4 Flash（OpenAI 兼容 base_url），JSON mode | 只做判断/建议/结论，重计算不碰 |
| 应用层 | FastAPI + pydantic v2 + 步骤状态机（session → Redis 可扩） | 每步 `run/confirm/artifact` 三端点 |
| 交互层 | Gradio 原型（Tabs+state 模拟卡片）→ **Vue3 stepper 正式版** | 快速验证→正式体验 |
| 执行层 | pandas / toad（WOE·IV）/ LightGBM / XGBoost / scikit-learn / SHAP，FastAPI 算法服务 | Dify code 沙箱装不了重型库——重计算一律外置 |
| 存储 | 本地版本化目录 → MinIO 可扩 | 快照/审计支撑 |
| Dify | **可选集成**：报告节点用行内 DeepSeek；或导出简化 DSL | v1 主路线降级原因见 §12 |

## 8. 核心数据契约

### 8.1 步骤状态机（会话核心）

```json
{
  "run_id": "run_20260916_001",
  "current_step": 5,
  "steps": {
    "1": {"status": "confirmed", "params": {...}, "artifact": "runs/.../step1_v1.json"},
    "4": {"status": "confirmed", "params": {"min_rows": 10000, "miss_drop": 0.8}, "artifact": "..."},
    "5": {"status": "running",    "params": {"bin_method": "chi2", "iv_threshold": 0.02}},
    "6": {"status": "dirty",      "reason": "上游 step5 参数变更"},
    "7": {"status": "dirty",      "reason": "上游 step5 参数变更"}
  }
}
```

状态集合：`pending / running / awaiting_confirm / confirmed / dirty / rejected`。

### 8.2 每步统一产物（artifact）

```json
{
  "step": 5,
  "params_snapshot": {...},
  "outputs": {"cleaned_data": "path", "pipeline": "path", "kept_features": [...]},
  "preview": {"charts": ["iv_bar.png", "woe_f1.png"], "table_head": [...], "n_rows": 38210},
  "conclusion_md": "共剔除 12 列缺失率>80%，剩 38 列，建议保留",
  "decided_at": "2026-09-16T12:00:00", "decided_by": "5527sy"
}
```

### 8.3 路由器输出（v1 继承）

`{paradigm, confidence, rationale, matched_template, clarifying_questions, source}` —— 详见 v1 技术细节文档 §3.1。

## 10. 里程碑

| 阶段 | 内容 | 验收 |

## 12. v1 → v2 演进对照

| 维度 | v1（bank-analysis-agent） | v2（data-flow-agent） |
|---|---|---|
| 产品形态 | 需求 → 生成 Dify 工作流 DSL，去 Dify 执行 | **自研卡片式向导产品**，全流程站内完成 |
| 执行层 | HTTP 调算法服务（无重算实现） | 算法服务落地：toad/LGB/XGB/OOT/SHAP 真算 |
| 流程粒度 | 一条 7 节点 DAG 一次跑完 | 七张卡片**逐卡拍板**，参数每步可调 |
| 数据接入 | 人工上传后直进分析 | 新增**样本设计（防标签泄漏）+ 数据体检**环节 |
| 交互 | 单对话框 | 向导式人机共驾 + 快照回溯 + 审计日志 + 涟漪过期 |
| Dify 角色 | 主路线执行平台 | 降级为可选集成（报告/导出） |
| 验证方法 | 5 折 CV | 5 折 CV 调参 + **OOT 时间外验证** |
